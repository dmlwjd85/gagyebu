# 배포 절차

쓱 가계부는 **보안 규칙(Firestore)** 과 **앱(GitHub Pages)** 을 따로 배포해요.
앱이 규칙보다 먼저 나가면, 새 앱의 쓰기(자동 기록의 `origin` 표식, 반복의 `skipped` 등)가 예전 규칙에 거부돼요.
그래서 **늘 규칙을 먼저, 앱을 나중에** 배포해요.

## 순서를 지키게 하는 장치
- 앱 배포 워크플로(`.github/workflows/deploy-pages.yml`)는 `rules` 단계가 성공해야 앱을 빌드·배포해요.
  - 비밀값 `FIREBASE_SERVICE_ACCOUNT`(서비스 계정 JSON)가 있으면 이 단계에서 규칙을 먼저 배포해요.
  - 없으면(지금 상태) `.github/firestore-rules-deployed.sha256`이 지금 `firestore.rules`와 같은지만 확인해요.
    다르면 멈추고 앱은 배포하지 않아요. 예전 앱이 그대로 남으니 데이터는 안전해요.
- CI(`ci.yml`)는 이 브랜치의 규칙이 아직 배포되지 않았으면 경고를 띄워요(실패로 치지는 않아요).
- 표시 파일은 `npm run rules:deploy`가 규칙 배포에 성공했을 때만 고쳐 써요. 손으로 고치지 마세요.
  (이 표시는 사람이 순서를 지켰다는 기록이라, 서비스 계정 방식처럼 실제 배포를 확인하지는 못해요.)

## 체크리스트 (규칙이 바뀐 PR)
1. [ ] PR의 CI가 모두 성공했는지 확인해요(단위·규칙 테스트·빌드).
2. [ ] PR 브랜치에서 규칙을 먼저 배포해요.
   ```bash
   npx firebase login            # 처음 한 번
   npm run rules:deploy          # = firebase deploy --only firestore:rules --project gagyebu-b44fc2 + 표시 파일 갱신
   ```
3. [ ] 바뀐 `.github/firestore-rules-deployed.sha256`을 같은 PR에 커밋·푸시해요.
   - 커밋 메시지 예: `규칙 배포 표시 갱신(운영에 규칙 배포함)`
4. [ ] Firebase 콘솔 › Firestore › 규칙에서 방금 배포한 내용과 시간이 맞는지 봐요.
5. [ ] 이제 PR을 머지해요. main에 들어가면 앱 배포 워크플로가 `rules` 확인 → 빌드 → Pages 배포 순서로 돌아요.
6. [ ] 배포가 끝나면 실제 주소에서 한 번 새로 고쳐서 새 버전이 뜨는지 봐요(설정 아래 버전 표시).

## 규칙이 바뀌지 않은 PR
- 표시 파일이 이미 같으니 그냥 머지하면 돼요.

## 되돌리기
- 앱만 되돌릴 때: main에서 되돌리는 커밋을 올려요. 규칙은 새 앱·예전 앱 모두 받아 주는 쪽(새 규칙)으로 두는 편이 안전해요.
- 규칙을 되돌릴 때: 앱도 함께 예전으로 돌려야 해요(새 앱 + 예전 규칙이면 자동 기록이 쌓이지 못하고 다음에 다시 시도해요).
