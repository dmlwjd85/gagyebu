# 배포 절차

쓱 가계부는 **보안 규칙(Firestore)** 과 **앱(GitHub Pages)** 을 따로 배포해요.
앱이 규칙보다 먼저 나가면, 새 앱의 쓰기(자동 기록의 `origin` 표식, 반복의 `skipped` 등)가 예전 규칙에 거부돼요.
그래서 **늘 규칙을 먼저, 앱을 나중에** 배포해요.

## 순서를 지키게 하는 장치
앱 배포 워크플로(`.github/workflows/deploy-pages.yml`)는 `rules` 단계가 성공해야 앱을 빌드·배포해요. 이 단계는 두 가지로 돌아요.

| 방식 | 언제 | 하는 일 | 믿을 수 있는 정도 |
|---|---|---|---|
| **직접 배포(추천)** | 저장소 비밀값 `FIREBASE_SERVICE_ACCOUNT`가 있을 때 | main의 규칙을 운영에 직접 배포하고, 성공해야 앱을 빌드·배포해요. 표시 파일은 보지 않아요. | 운영 규칙이 늘 main과 같아요 |
| 표시 파일 관문 | 비밀값이 없을 때(**지금**) | `.github/firestore-rules-deployed.sha256`의 값이 지금 지문과 같을 때만 앱을 배포해요. 다르면 멈추고, 예전 앱이 그대로 남아요. | 사람이 남긴 기록이라 실제 배포를 증명하지는 못해요 |

- 지문은 `firestore.rules`와 `firebase.json`의 `firestore` 설정(규칙·색인 파일 경로), 그 설정이 가리키는 파일(색인 파일이 생기면 그것도)을 함께 계산해요. 에뮬레이터 설정은 넣지 않아요(`scripts/rules-mark.mjs`).
- CI(`ci.yml`)는 이 브랜치의 규칙이 아직 배포되지 않았으면 경고를 띄워요(실패로 치지는 않아요).

### 표시 파일 규칙 (꼭 지켜요)
- **표시 파일은 손으로 고치지 않아요.** `node scripts/rules-mark.mjs`만 따로 돌리지도 않아요.
- 표시 파일을 바꾸는 방법은 **`npm run rules:deploy` 하나뿐**이에요. 이 명령은 규칙 배포가 성공해야만 표시를 고쳐요.
- 표시만 커밋하면 관문은 통과하지만, 운영 규칙은 예전 그대로라 새 앱의 쓰기가 거부돼요. 리뷰할 때 표시 파일이 바뀐 커밋은 rules:deploy 출력(배포 시간)과 Firebase 콘솔의 규칙 배포 기록이 맞는지 확인해요.

### 비밀값 넣는 방법 (추천, 한 번만)
표시 파일 관문의 빈틈을 없애는 방법이에요. 저장소 관리자가 직접 해요.
1. Google Cloud 콘솔 › 프로젝트 `gagyebu-b44fc2` › IAM 및 관리자 › 서비스 계정에서 새 서비스 계정을 만들어요(예: `github-rules-deploy`).
2. 역할은 꼭 필요한 것만 줘요.
   - **Firebase Rules 관리자**(`roles/firebaserules.admin`): 규칙 배포
   - **Service Usage 소비자**(`roles/serviceusage.serviceUsageConsumer`): Firebase CLI가 API 상태를 확인할 때 필요
   - 소유자·편집자 역할은 주지 않아요.
3. 그 서비스 계정의 키(JSON)를 하나 만들어 내려받아요.
4. GitHub 저장소 › Settings › Secrets and variables › Actions › New repository secret
   - 이름: `FIREBASE_SERVICE_ACCOUNT`
   - 값: 내려받은 JSON 파일 내용 전체
5. 내려받은 키 파일은 바로 지워요. 키는 저장소나 다른 곳에 올리지 않아요.
6. 다음 main 배포부터 `rules` 단계가 "규칙 먼저 배포"로 돌아요. 워크플로 기록에서 확인해요.
   - 넣은 뒤에는 체크리스트 2~3번(직접 rules:deploy·표시 커밋)이 필요 없어요. 머지하면 규칙 → 앱 순서로 자동 배포돼요.

## 체크리스트 (규칙이 바뀐 PR)
1. [ ] PR의 CI가 모두 성공했는지 확인해요(단위·규칙 테스트·빌드).
2. [ ] PR 브랜치에서 규칙을 먼저 배포해요.
   ```bash
   npx firebase login            # 처음 한 번
   npm run rules:deploy          # = firebase deploy --only firestore:rules --project gagyebu-b44fc2 + 표시 파일 갱신
   ```
3. [ ] 바뀐 `.github/firestore-rules-deployed.sha256`을 같은 PR에 커밋·푸시해요.
   - 커밋 메시지 예: `규칙 배포 표시 갱신(운영에 규칙 배포함)`
4. [ ] Firebase 콘솔 › Firestore › 규칙에서 방금 배포한 내용과 시간이 맞는지 봐요.
5. [ ] 이제 PR을 머지해요. main에 들어가면 앱 배포 워크플로가 `rules` 확인 → 빌드 → Pages 배포 순서로 돌아요.
6. [ ] 배포가 끝나면 실제 주소에서 새로 고쳐서 새 버전이 뜨는지 봐요. 설정 맨 아래 '쓱 가계부 v0.0.1 · 커밋 7자리'가 머지 커밋과 같은지 봐요.
   - PR #8을 처음 배포할 때만 **두 번** 새로 고쳐야 해요. 지금 깔린 640ff0f의 서비스 워커는 새 버전을 기다리게 두는 설정이라, 첫 새로 고침에서는 새 워커가 설치만 되고 화면은 옛 버전이에요(로그인 상태에서도 같아요).
   - 그다음 배포부터는 로그인 여부와 상관없이 새로 고침 한 번이면 돼요(`tools/qa/sw_update.py` 경우 B·E 실측).
   - 앱을 켜 둔 채 새 버전이 나오면 '새 버전이 있어요 [지금 적용]'이 떠요. 입력 중이 아니면 앱을 뒤로 보냈다 오는 사이에 알아서 바뀌어요(경우 F).
   - 입력 시트·대화상자가 열려 있거나 값을 적는 중이면 바꾸지 않고 기다려요. 뒤로 보냈다 와도 적던 값은 그대로예요(경우 C·C').

## 규칙이 바뀌지 않은 PR
- 표시 파일이 이미 같으니 그냥 머지하면 돼요.

## 되돌리기
- 앱만 되돌릴 때: main에서 되돌리는 커밋을 올려요. 규칙은 새 앱·예전 앱 모두 받아 주는 쪽(새 규칙)으로 두는 편이 안전해요.
- 규칙을 되돌릴 때: 앱도 함께 예전으로 돌려야 해요(새 앱 + 예전 규칙이면 자동 기록이 쌓이지 못하고 다음에 다시 시도해요).

## PR #8 롤아웃: 바뀌는 동안 예전 앱에서 생기는 일
규칙을 먼저 배포하면, 사용자 기기에 남아 있는 예전 앱(지금 배포본 640ff0f)이 잠깐 새 규칙과 함께 돌아요.
아래는 `tools/qa/old_limits.py`·`tools/qa/old_undo.py`로 에뮬레이터에서 실제로 확인한 내용이에요.

| # | 예전 앱에서 하는 일 | 실제로 생기는 일 | 언제 풀리나 |
|---|---|---|---|
| ① | 자동 기록을 지워요 | 지운 달이 반복의 '지운 달' 목록에 남지 않아요. 새 앱을 다시 열어도 그 달은 이미 지나간 달이라 다시 생기지 않아요(실측). 다만 다른 기기에 그 달 자동 기록이 오프라인으로 쌓여 있었다면, 그 기기가 연결될 때 다시 생길 수 있어요. | 새 앱에서 지우면 다시 생기지 않아요 |
| ② | 앱을 열어 반복을 자동 기록해요 | 640ff0f는 모든 반복의 모든 달을 **한 묶음**으로 써요. 한 반복의 그 달 기록이 이미 있으면(예: 직접 고친 관리비 10월) 묶음 전체가 거부돼서, **다른 반복(넷플릭스 등)도 기록되지 않고** 열 때마다 '저장이 거부됐어요. 문제가 계속되면 알려 주세요.'가 떠요(실측: 두 번 열어도 같음). 데이터가 지워지거나 덮이지는 않아요. | 새 앱을 열면 빠진 달이 모두 기록되고 토스트도 사라져요(실측: 넷플릭스 10월 13,500원 생김, 관리비 81,000원 그대로) |
| ③ | 반복을 고쳐 저장해요 | 반복 문서를 통째로 다시 써서 '지운 달' 목록이 지워져요(실측: ['2026-09'] → 없음). 그 달은 이미 lastPosted가 지나 있어 바로 되살아나지는 않아요. | 새 앱에서 다시 지우면 목록에 다시 남아요 |
| ④ | createdAt 없는 기록을 고친 뒤 [되돌리기] | 640ff0f는 문제없이 같은 기록으로 되돌려요(실측). 이 PR의 중간 빌드(941dd7f, main에 들어간 적 없음)는 같은 칸에 못 써서 새 기록을 하나 더 만들었는데(금액 두 번), 규칙을 고쳐 이제 같은 칸에 되돌려져요(실측). | 해결됨 |

- 이 기간을 줄이려면 규칙 배포 바로 뒤에 앱을 배포해요(체크리스트 2~5번을 이어서).
- 예전 앱은 사용자가 두 번 새로 고치거나, 앱을 닫았다가 두 번 열면 새 앱으로 바뀌어요(`tools/qa/sw_update.py` 경우 A 실측). '새로 고치면 바로 해결'은 이번 전환에서는 맞지 않아서, 안내할 때는 "두 번 새로 고쳐 주세요"라고 해요.
